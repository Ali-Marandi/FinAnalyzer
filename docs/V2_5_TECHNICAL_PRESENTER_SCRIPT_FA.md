# اسکریپت کامل ارائه فنی FinAnalyzer Enterprise v2.5.0

**مخاطب:** مدیر فناوری، مدیر امنیت، CFO، تیم مالی، تیم release و هیئت راهبری محصول
**زمان پیشنهادی:** ۱۲ تا ۱۵ دقیقه، به‌علاوه ۵ دقیقه پرسش و پاسخ
**هدف:** نشان‌دادن اینکه FinAnalyzer v2.5.0 کنترل‌های امنیتی را از یک ادعای معماری به جریان‌های عملیاتی قابل‌راستی‌آزمایی—از login تا close حسابداری و artifact Windows—تبدیل کرده است.

> **نکته ارائه‌دهنده:** این ارائه یک مرور فنی است، نه گزارش حسابرسی یا تضمین انطباق قانونی. در توضیح قابلیت‌ها، همواره بین «کنترل پیاده‌سازی‌شده» و «کنترل پیشنهادی برای استقرار مشتری» تمایز برقرار کنید.

## اسلاید ۱ — FinAnalyzer Enterprise v2.5.0

**زمان: ۶۰ ثانیه**

سلام. امروز نسخه ۲.۵.۰ FinAnalyzer Enterprise را مرور می‌کنم؛ نسخه‌ای که سه مسیر مهم را به هم متصل می‌کند: امنیت قابل‌راستی‌آزمایی، انتشار کنترل‌شده Windows و کنترل بستن دوره مالی. پیام اصلی این است که نرم‌افزار مالی سازمانی فقط با ثبت داده یا ایجاد گزارش قابل‌اتکا نمی‌شود. اعتماد زمانی شکل می‌گیرد که بتوانیم مشخص کنیم چه کسی، با چه session و مجوزی، در کدام شرکت، چه عملیات حساسی را انجام داده و آیا فایل اجرایی منتشرشده نیز همان فایلی است که فرآیند build و امضا را پشت سر گذاشته است.

در این ارائه ابتدا تحول audit را توضیح می‌دهم. سپس DPAPI و HMAC chain را بررسی می‌کنم. بعد به انتشار EXE امضاشده و تست‌ها می‌رسیم. در بخش پایانی، قابلیت جدید Period Close Controls و نقشه‌راه تجاری را نشان می‌دهم.

## اسلاید ۲ — امنیت از لاگ به شواهد

**زمان: ۸۰ ثانیه**

در مدل‌های قدیمی، audit اغلب به چند پیام متنی محدود است؛ مانند «کاربر وارد شد» یا «دسترسی رد شد». این پیام‌ها برای troubleshooting مفیدند، اما برای بررسی incident یا پاسخ‌گویی انطباقی کافی نیستند. مشخص نیست رخداد در کدام company scope بوده، session چه بوده، هدف عملیات کدام object بوده یا آیا ترتیب رخدادها تغییر کرده است.

در نسخه ۲.۵.۰، که بر پایه audit v2.4 ساخته شده، رخدادها ساختاریافته‌اند. هر event شامل شناسه مستقل، sequence، actor، company، session، category، severity، outcome، source و target است. این مدل باعث می‌شود تیم امنیت و تیم مالی با یک زبان مشترک صحبت کنند. برای نمونه، می‌توانیم تمام رویدادهای denied مربوط به یک company یا تمام رخدادهای یک request close را جداگانه بررسی کنیم.

نکته مهم این است که ساختاریافتگی به‌تنهایی امنیت نیست؛ اما پیش‌شرط ایجاد شواهد قابل‌جست‌وجو و قابل‌بررسی است.

## اسلاید ۳ — زنجیره HMAC-SHA256

**زمان: ۹۰ ثانیه**

در این اسلاید، تفاوت میان ثبت رویداد و ثبت tamper-evident را می‌بینیم. هر رخداد audit یک `event_hash` دارد که با HMAC-SHA256 روی payload استانداردشده محاسبه می‌شود. payload رخداد جدید شامل `previous_hash` رخداد قبلی نیز هست. بنابراین رخدادها فقط کنار هم قرار نگرفته‌اند؛ به هم متصل‌اند.

اگر کسی محتوای یک event را تغییر دهد، event hash آن دیگر معتبر نیست. اگر کسی رکوردی را حذف کند یا ترتیب را جابه‌جا کند، اتصال `previous_hash` و sequence شکسته می‌شود. متد `verify_chain()` این حالت‌ها را بررسی می‌کند و نخستین sequence ناسالم را گزارش می‌دهد.

این مکانیزم جایگزین ذخیره‌سازی غیرقابل‌تغییر خارجی یا SIEM نیست؛ ولی یک کنترل کاربردی در لایه برنامه است. برای استقرار enterprise، export دوره‌ای evidence به فضای نگهداری مستقل و محدودکردن دسترسی نوشتن به database، گام‌های تکمیلی مهم هستند.

## اسلاید ۴ — DPAPI و redaction

**زمان: ۹۰ ثانیه**

HMAC فقط به اندازه حفاظت از کلید خود معتبر است. در Windows، FinAnalyzer از DPAPI برای محافظت از کلید محلی امضای audit استفاده می‌کند. این کار key material را به پروفایل Windows یا محدوده محافظت‌شده سیستم گره می‌زند و از قرار دادن کلید خام در repository یا release package جلوگیری می‌کند.

اما محافظت از کلید کافی نیست. audit نباید خودش به یک مخزن secret تبدیل شود. بنابراین logger مقادیری مانند access token، refresh token، password، client secret، cookie و authorization header را قبل از ذخیره redact می‌کند. ما در log، context عملیاتی حداقلی را نگه می‌داریم، نه اعتبارنامه را.

در نتیجه، DPAPI مسئله حفاظت از کلید محلی را پوشش می‌دهد و redaction مسئله حداقل‌سازی داده ثبت‌شده را. این دو کنترل مکمل یکدیگرند، نه جایگزین هم.

## اسلاید ۵ — امنیت در جریان واقعی محصول

**زمان: ۸۰ ثانیه**

در این اسلاید نشان می‌دهیم که security فقط یک صفحه تنظیمات نیست. AuthorizationService با الگوی deny-by-default اجرا می‌شود. بنابراین permission تعریف‌نشده، membership غیرفعال یا scope نادرست، به‌صورت پیش‌فرض رد می‌شود. عملیات حساس نیز به evidence MFA نیاز دارند.

در لایه identity، ورود SSO، خروج session و خطاهای login با رویداد ساختاریافته ثبت می‌شوند؛ بدون آنکه token IdP در audit ذخیره شود. در جریان Plaid، اتصال، sync، unlink و failureها context کاربر و شرکت را دارند. در گزارش‌دهی نیز تولید، زمان‌بندی و تحویل خارجی از همان مدل audit پیروی می‌کنند.

این رویکرد به ما اجازه می‌دهد یک incident را از decision دسترسی تا اثر عملیاتی دنبال کنیم. برای نمونه، اگر اتصال بانکی یا تحویل گزارش نیاز به بررسی داشته باشد، actor، session و outcome در همان مدل قابل جست‌وجو هستند.

## اسلاید ۶ — زنجیره تأمین و انتشار Windows

**زمان: ۱۱۰ ثانیه**

اکنون از امنیت runtime به امنیت artifact می‌رسیم. پیش از ساخت EXE، dependency gate baseline پروژه را کنترل می‌کند: `pypdf` و `wheel` در نسخه امن تعیین‌شده باشند و `xhtml2pdf` در build استفاده نشود. اگر gate یا `pip-audit` شکست بخورد، build باید متوقف شود.

برای release رسمی، توصیه ما جداسازی Build VM و Signing VM است. Build VM از source و tag تأییدشده، test و dependency verification را اجرا می‌کند. سپس artifact با SHA-256 به Signing VM منتقل می‌شود. آنجا SignTool فایل را با Authenticode، `/fd SHA256` و timestamp RFC 3161 با `/tr` و `/td SHA256` امضا می‌کند.

Microsoft توضیح می‌دهد که SignTool امکان امضا، timestamp و verify را فراهم می‌کند و برای buildهای جدید مشخص‌کردن digest الگوریتم ضروری است.[1] timestamp نیز مهم است، زیرا بدون آن با پایان اعتبار گواهی، Windows فایل را unsigned در نظر می‌گیرد.[2]

## اسلاید ۷ — اعتبارسنجی قابل‌اندازه‌گیری

**زمان: ۸۰ ثانیه**

در امنیت محصول، تست سبز به‌تنهایی کافی نیست، اما شرط لازم است. در validation کامل فعلی پروژه، ۲۰ تست واحد و یکپارچه موفق اجرا شده است. این پوشش، audit chain، tamper detection، redaction، RBAC، SSO/MFA، Plaid، گزارش‌دهی و Period Close را شامل می‌شود.

برای Period Close، علاوه بر مسیر موفق، سناریوهای منفی را نیز آزمایش کرده‌ایم: self-approval، self-rejection، MFA منقضی، درخواست فعال تکراری و خطای accounting وسط اجرای close. در حالت خطای accounting، وضعیت approval، قفل سال مالی و event موفق execution همگی rollback می‌شوند. این آزمایش نشان می‌دهد که atomicity فقط یک comment در کد نیست.

پیام این اسلاید روشن است: build قابل انتشار باید test، dependency gate، signing و verification مستقل را هم‌زمان پشت سر بگذارد.

## اسلاید ۸ — کنترل بستن دوره با دو نفر مستقل

**زمان: ۱۲۰ ثانیه**

این مهم‌ترین قابلیت تجاری جدید نسخه ۲.۵.۰ است. بستن دوره مالی یک تغییر برگشت‌ناپذیر یا پرریسک است؛ بنابراین نباید با یک کلیک و توسط همان شخصی که درخواست را ساخته انجام شود.

در مرحله اول، Preparer با permission `ledger.period.close.request` و MFA تازه درخواست را ایجاد می‌کند. سیستم بررسی می‌کند سال مالی باز است، حساب retained earnings فعال و از نوع equity است و هر دو در company scope درست قرار دارند.

در مرحله دوم، یک Financial Controller مستقل با permission `ledger.period.close.approve` و MFA تازه تصمیم می‌گیرد. سرویس user ID درخواست‌کننده و تأییدکننده را مقایسه می‌کند. اگر یکسان باشند، عملیات مسدود می‌شود، درخواست در حالت Pending باقی می‌ماند و رخداد `period_close.sod_violation` با outcome `denied` در HMAC chain ثبت می‌شود.

در مرحله سوم، اگر approval مستقل معتبر باشد، closing entry، قفل سال مالی، وضعیت workflow و audit success در یک تراکنش هماهنگ ثبت می‌شوند. اگر accounting failure رخ دهد، context manager transaction همه این تغییرات را rollback می‌کند.

## اسلاید ۹ — نقشه‌راه تجاری

**زمان: ۸۰ ثانیه**

Period Close Control نقطه شروع یک الگوی محصول است: هر عملیات مالی پرریسک باید به workflow کنترل‌شده، مجوز صریح و evidence قابل‌بررسی تبدیل شود.

اولویت بعدی، Bank Reconciliation Workbench است. اتصال بانکی فقط داده وارد می‌کند؛ محصول enterprise باید matching قابل‌توضیح، صف exception، override ممیزی‌شده و مسئولیت مشخص ایجاد کند. پس از آن، AP Approvals و rolling cash forecast بیشترین ارزش را برای مدیر مالی و کنترل نقدینگی ایجاد می‌کنند.

در موج مقیاس، multi-entity consolidation، elimination entries و close calendar با evidence مطرح می‌شوند. در همه این قابلیت‌ها، چهار اصل تغییر نمی‌کنند: MFA برای عملیات حساس، تفکیک وظایف، scope شرکت و audit chain.

## اسلاید ۱۰ — گام بعدی

**زمان: ۶۰ ثانیه**

در جمع‌بندی، FinAnalyzer v2.5.0 سه لایه را به‌هم متصل می‌کند: حفاظت از عملیات، حفاظت از evidence و حفاظت از artifact انتشار. Period Close Controls نشان می‌دهد این معماری فقط برای log یا settings نیست؛ می‌تواند در حساس‌ترین workflow مالی نیز اعمال شود.

گام اجرایی بعدی روشن است: build از tag تأییدشده در VM ایزوله، عبور از dependency gate و تست‌ها، امضا با certificate سازمانی، RFC 3161 timestamp، verification مستقل و سپس انتشار SHA-256 همراه EXE. این فرآیند باید بخشی از release playbook سازمان باشد، نه یک فعالیت دستی موردی.

از تیم راهبری درخواست می‌کنیم سه تصمیم بگیرد: تأیید مدل Signing VM و گواهی سازمانی، اولویت‌دادن به Bank Reconciliation Workbench در چرخه بعدی، و تعیین policy نگهداری evidence audit و release. با این تصمیم‌ها، مسیر توسعه از یک desktop accounting application به یک پلتفرم مالی سازمانی کنترل‌شده روشن می‌شود.

## پاسخ‌های کوتاه برای پرسش‌های متداول

| پرسش | پاسخ پیشنهادی |
|---|---|
| آیا HMAC chain مانع همه نوع دست‌کاری می‌شود؟ | تغییر یا گسست رخدادهای درون زنجیره را آشکار می‌کند؛ برای دفاع جامع‌تر، database access، export مستقل و retention policy نیز لازم است. |
| چرا MFA ۱۵ دقیقه است؟ | عملیات close حساس است؛ زمان کوتاه، ریسک استفاده از session فراموش‌شده یا واگذارشده را کاهش می‌دهد. مقدار policy قابل بازبینی سازمانی است. |
| آیا یک Company Admin می‌تواند درخواست خودش را approve کند؟ | خیر. SoD بر اساس user ID اعمال می‌شود، نه صرفاً role. Admin نیز برای درخواست خودش rejected می‌شود. |
| آیا EXE هم‌اکنون امضاشده است؟ | source و automation آماده‌اند؛ امضای واقعی باید در Windows clean با گواهی سازمانی انجام شود. Private key در repository یا محیط توسعه نگهداری نمی‌شود. |
| اگر اجرای accounting شکست بخورد چه می‌شود؟ | transaction rollback می‌شود؛ درخواست pending، سال مالی باز و success audit execution ثبت‌نشده باقی می‌مانند. |
